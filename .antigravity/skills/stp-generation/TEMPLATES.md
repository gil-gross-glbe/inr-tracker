## Detailed Section Guidance

### 1. 🎯 Purpose
Brief statement of what STP covers, reference to epic/story, quality standards. Extract from Jira epic/story title and description.

### 2. 📌 Scope
**In Scope:** Clear list of what will be tested. **Out of Scope:** Explicitly state what is NOT covered. Extract from Jira acceptance criteria, Physical Design scope section.

### 3. ✅ Objectives
Business objectives (business value validation), technical objectives (technical requirements verification), quality objectives (quality standards). Extract from Jira acceptance criteria, epic description, Physical Design.

### 4. 🧪 Test Approach
Unit Testing (developer), Integration Testing (QA + developer), Regression Testing (QA), End-to-End/Performance/Security Testing (if applicable). Extract from Physical Design integration points, architecture decisions.

### 5. 📅 Schedule
Timeline for testing activities, key milestones, owner assignments, dependencies. If timeline is TBD, use placeholder but maintain structure. Extract from sprint planning, Epic timeline from Jira.

### 6. 📝 Test Scenarios
Detailed test cases organized by feature/area. Each test case: Test Case ID, Test Steps, Expected Result. Grouped into logical sections with icons. Test Case Naming: "TC-1 [Feature] [Scenario] [Condition]", number sequentially. Extract from Jira acceptance criteria, Physical Design, comments/discussions, similar features.

### 7. 👥 Responsibilities
QA Engineer (test execution, defect reporting), Product Owner (validation), Developer/Tech Lead (technical support, unit testing), QA Lead/Architect (if applicable). Use `@username` format or Confluence mention format. Extract from Jira assignees, team structure.

### 8. ⚠️ Risks
Potential risks impacting testing/quality: technical, timeline, resource, integration risks. Risk severity indicators (optional). Extract from team discussions, technical complexity assessment, historical issues, dependencies.

### 9. ✔️ Acceptance Criteria
Clear definition of when epic/story is successfully tested, pass/fail criteria, quality gates. Extract from Jira acceptance criteria, Definition of Done, quality standards.

### 10. ✍️ Sign-Off
Prepared by (QA Engineer), Approved by PM/Product Owner, Approved by QA Lead (if applicable). Extract from team structure, approval workflow.

### 11. 📝 Document Metadata
Skill version (from SKILL.md frontmatter), generation date, AI model name (detect dynamically - use actual model executing this skill). Purpose: traceability, debugging, historical context.

## Formatting Guidelines

- **Section Headers**: Always include icon before section number: `1. 🎯 **Purpose**`
- **Confluence Mentions**: Use `<ac:link><ri:user ri:account-id="[ACCOUNT-ID]"/></ac:link>` format or `@username` format
- **Jira Links**: Use `[CORE-XXXX](https://global-e.atlassian.net/browse/CORE-XXXX)` format
- **Test Scenarios Table**: Use markdown table format with columns: Test Case, Test Steps, Expected Result
- **Section Numbering**: Use numbered list format with icons (1. 🎯, 2. 📌, 3. ✅, etc.)
- **Bold Headers**: Use `**Header**` for section headers with icons
- **Test Scenario Sections**: Use format: `### Section X: [ICON] [Section Name]`
- **Epic Information Header**: Use `## 📋 Epic Information` for epic/story details section

## Test Scenarios Format

For each test scenario, create a table entry with 5 columns:

**⚠️ CRITICAL: Multi-line Content in Tables:**
- **DO NOT use `\n` for line breaks in markdown tables** - markdown tables do not render `\n` as line breaks
- **USE `<br>` tags instead** - HTML `<br>` tags work correctly in both markdown and Confluence tables
- **Format:** Use `<br>` between numbered steps and between multiple expected results

```markdown
| **Test Case** | **Test Steps** | **Expected Result** | **Test Level** | **Priority** |
| --- | --- | --- | --- | --- |
| TC-1 [Test Name] | 1. Step one<br>2. Step two<br>3. Step three | Expected outcome description<br>Additional verification point | Integration | Must |
```

### Test Level Column

Assign appropriate test level based on what is being tested:
- **Unit**: Individual components, methods, functions (developer responsibility)
- **Integration**: Interactions between components, services, systems
- **Functional**: End-to-end user flows, business processes (QA responsibility)
- **Performance**: Performance, load, stress scenarios
- **Security**: Security vulnerabilities, access controls
- **Regression**: Existing functionality validation
- **E2E**: Complete end-to-end user journeys

### Priority Column

Assign priority based on criticality:
- **Must**: Critical test case that must pass before release
- **Should**: Important test case that should be executed
- **Nice to Have**: Optional test case if time permits
- **P0/P1/P2**: Alternative priority levels (P0 = Critical, P1 = High, P2 = Medium)

### Test Level Assignment Guidelines

- Extract from Physical Design: Integration points → Integration tests, API endpoints → Integration tests, Functions/methods → Unit tests
- Extract from Acceptance Criteria: User flows → Functional tests, Business rules → Functional tests
- Extract from Story Description: Edge cases → Functional/Integration tests, Performance concerns → Performance tests
- Default to Functional for most QA test cases unless clearly specified otherwise

**See Also:** [EXAMPLES.md](EXAMPLES.md#test-scenario-extraction) for detailed extraction patterns and examples.

### Test Scenario Section Formatting

- Use icons for section headers: `### Section 1: 🚩 LaunchDarkly Feature Flag Validation`
- Add brief description after section name if helpful: `*Feature flag enablement/disablement testing*`
- Number test cases sequentially: TC-1, TC-2, TC-3... (or TC-1.1, TC-1.2 if using section prefixes)

Group related test scenarios into sections with appropriate icons:
- 🚩 Feature Toggle/Flag Validation
- ⚙️ Configuration Testing
- 🔄 Integration Testing
- 🎨 Functional Validation
- 🔍 Edge Cases and Negative Testing
- 👤 Shopper/User Experience Validation
- 🔄 Regression Testing
- 🧩 Unit Testing Areas

## Quality Pre-Flight Checks

**Run these checks before creating Confluence page.**

**Content Completeness:** All 11 sections present and populated, all sections include icons, no placeholder text, Purpose clear, Scope has both "In Scope" and "Out of Scope", Epic scope validated (if Epic), Test Scenarios has at least 3 test cases with Test Steps and Expected Results, Responsibilities has QA Engineer and Product Owner, Acceptance Criteria populated, Schedule structured, Document Metadata includes skill version and generation date

**Formatting Quality:** All section headers include icons, test scenario sections include icons, all Jira/Confluence links properly formatted, team member @mentions correct, test scenario tables formatted, section numbering correct, risk items include severity icons if applicable, no broken markdown syntax

**Link Validation:** Epic/Story link correct, Physical Design link valid (if present), all referenced Confluence pages exist, TestRail links valid (if present)

**Information Accuracy:** Team member names match Jira users, Sprint/Version accurate, test scenarios match acceptance criteria, conflicts resolved and documented

**Test Scenario Quality:** Clear actionable steps, specific verifiable expected results, cover positive/negative/edge cases, Unit/Integration/Functional tests identified, logically grouped, no duplicate test scenarios

**Duplicate Detection:** Extract all test scenarios, compare within sections (exact/near-duplicates), compare across sections (cross-section duplicates), handle duplicates (remove exact duplicates, review near-duplicates, keep cross-section duplicates in most appropriate section), renumber test cases sequentially after removal (no gaps), report to user

**If checks fail:** List failures, fix automatically if possible (especially duplicates), ask user for clarification on issues that can't be auto-fixed, do not create Confluence page until all checks pass

   QA Engineer: [Name] (extracted from Jira fields)

### Summary Report Requirements

**Rules:** Always include all sections (use "TBD" or "Not available" if data missing), use exact section headers (copy emoji and text exactly), required fields marked (REQUIRED) must be present, optional sections use conditional format `[If condition:]`, consistent formatting (✅ success, ⚠️ warnings, ❌ failures), no empty sections (show "None" or "TBD"), counts must match (verify test scenario counts match between sections), links must be valid and clickable, local file links use `file:///` protocol with forward slashes, generation time required (calculate from start to finish), status indicators consistent (✅ PASSED, ⚠️ WARNING, ❌ FAILED)

**Before generating:** Read template structure, copy template exactly, fill in all placeholders, verify all sections present, verify counts match, verify links valid

**When to generate:** Before Confluence Creation (show summary, get approval, then create), After Confluence Creation (show summary with Confluence links), For Bulk Operations (show summary for each STP + overall summary)

**Consistency Rules:** Template compliance (exact format, no modifications), field population (use "TBD"/"Not available"/"None" for missing optional fields), conditional sections (show only when condition true), status icons (✅ success, ⚠️ warnings, ❌ failures), counts verification (accurate and matching), link formatting (markdown format `[Text](URL)`), date formatting (YYYY-MM-DD or "Last Modified: [date]"), time calculation (from start to completion), error handling (show error reason if section failed), no placeholders (replace with actual values or "TBD"/"Not available")
